### Key architectural decisions & patterns

- **Snowflake-centric, Snowpark-powered ETL**  
  - Standardized on **Snowflake + Snowpark (Python)** as the execution platform so heavy lifting (joins, aggregation, JSON processing) happens in-database, not on an app server.  
  - Encapsulated business logic in Snowpark workflows (`src/snowpark_workflows/workflows/*`) with **dual entry points**:  
    - `main(session, ...)` for production stored procedures.  
    - `__main__` blocks for local debugging against a real Snowflake session.  
  - **Benefit**: single code path runs identically in dev and prod, simplifying debugging and reducing “works locally but not in Snowflake” issues.

- **Canonical entity / attribute model**  
  - Modeled the domain around an `ENTITY` table (e.g. `ECOMMERCE / PRODUCT / ASIN`) and an `ATTRIBUTES` table for semi-structured payloads (e.g. Keepa JSON under `ATTR_SUB_TYPE='KEEPA'`).  
  - All workflows (product ingestion, enrichment, API calls) write into this model with clear lifecycle timestamps (`LOAD`, `END`, `"UPDATE"`).  
  - **Benefit**: this creates a single, extensible hub for all e‑commerce entities and attributes, making downstream analytics and future integrations straightforward.

- **Idempotent, restartable ETL design**  
  - Implemented a **terminate-then-reactivate** pattern in `CAT_TO_PRODUCTS`:  
    - Phase 1: mark all active product entities `END = CURRENT_TIMESTAMP()`.  
    - Phase 2: insert new ASINs, reactivate existing ones (`END = NULL`) based on the latest Keepa snapshot.  
  - In `PRODUCT_TO_ATTRIBUTES`, new KEEPA attribute rows are inserted, then older rows for those products are cleaned up in a single batched delete.  
  - **Benefit**: procedures can be rerun safely (nightly or on demand) without accumulating duplicates; state is always “current as of last successful run” while preserving history via timestamps.

- **API-aware, multi-strategy ingestion architecture**  
  - For category ingestion (`CAT_TO_PRODUCTS`), designed a **multi-strategy query engine** around Keepa’s 10-page limit:  
    - 6 configurable sort strategies (sales and monthly sold ascending/descending + combinations).  
    - Each strategy fetches up to 10 pages; a **global ASIN set** deduplicates across all strategies.  
  - Achieved ~50k–60k unique products per full run (≈75%+ coverage of the catalog) vs ≈10k (~15%) with a single strategy.  
  - **Benefit**: dramatically higher catalog coverage without breaking API constraints, while keeping the logic transparent and configurable.

- **Throughput and cost optimization (batching and rate limiting)**  
  - Replaced row-by-row inserts with **batched `INSERT … UNION ALL`** patterns for both `ENTITY` and `ATTRIBUTES`, grouping 20–100 records per statement depending on payload size.  
  - Eliminated per-row `MAX(ID)` lookups for attributes by using smarter “keep latest per product” cleanup SQL, reducing unnecessary queries by an order of magnitude.  
  - Implemented **token-based rate limiting** around the Keepa API (short waits when token balance is healthy, longer refill waits when low), tuned for thousands of products per run without hitting 429s.  
  - **Result**: end-to-end runtime for large batches improved from “tens of minutes with high variance” to **predictable, stable runs often 10–20x more efficient** at the database layer, while keeping API token usage under control.

- **Dynamic environment & schema handling**  
  - Enforced a **no hardcoded database/schema** rule: all SQL uses `session.get_current_database()` and `session.get_current_schema()` to build fully qualified table references at runtime.  
  - Mapped secrets and external access integrations (for outbound HTTP) via Snowflake constructs instead of embedding credentials in code.  
  - **Benefit**: the same procedures can be promoted from dev → test → prod with zero code changes; environment differences are handled by Snowflake roles, context, and secrets.

- **Schema synchronization and governance**  
  - Built a **schema sync tool** (`sync_snowflake_schema.py`) that exports tables, views, procedures, integrations, and secret metadata into versioned SQL/CSV/JSON under `data/schema_sync/` and `sql/tables/ddl/`.  
  - Integrated this into the workflow so developers can run a sync before/after changes and review diffs (e.g. table/column changes, new procedures) in git.  
  - **Benefit**: strong transparency and governance — the Snowflake environment is always backed by a human-readable, version-controlled snapshot, which greatly reduces drift and surprises during deployments.

- **Deployment pipeline & testing strategy**  
  - Developed deployment tooling in `infra/deploy/` to **bundle Snowpark workflows into single-file stored procedures** (`*_AUTO.sql`), automatically inlining dependencies and stripping local-only code.  
  - Extended this with targeted deployment scripts (e.g. for `EXC_SQL_STEPS` and other procedures) that:  
    - Create or replace the procedure.  
    - Load test data.  
    - Execute the procedure and validate return codes and logs (e.g. from `PROC_EXECUTION_LOG`).  
  - Set up `pytest` tests and SQL test scripts so each procedure has a repeatable verification path.  
  - **Benefit**: confident, low-friction deployments; procedures are treated much like application code with packaging, tests, and automated promotion.
