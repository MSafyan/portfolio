### **Technical Challenges Overcome**

#### **Schema Drift & Upstream Data Issues (Real Examples)**

**Inventory API Schema Mismatch — REST vs GraphQL**
- Initial ETL pulled inventory stock from Shopify REST API. Incoming inventory (stock in transit) was missing from REST responses.
- After days of investigation, discovered the incoming inventory field only existed in Shopify's GraphQL API — the REST endpoint simply didn't expose it.
- Had to redesign the inventory pipeline to call GraphQL for incoming stock and merge it with REST data, normalizing fields across both response shapes.

**Sales Number Mismatch — Gift Card Refund Classification**
- Monthly sales were in the millions. Each month there was a consistent 1-3% divergence between our REST API pipeline numbers and Shopify's own dashboard reports.
- Exported raw data from the Shopify dashboard, manually checked individual orders — some had returns/refunds but those didn't always explain the gap. Checking order-by-order from the dashboard didn't surface the pattern.
- Raised with Shopify support. Got a generic response. One support developer eventually hinted at GraphQL order changes as a potential source of truth discrepancy.
- Built Python scripts to query the affected orders through GraphQL's order changes API, populated the relevant fields, and compared against the REST data.
- Root cause: refunds processed as gift cards were being classified inconsistently — sometimes a refund was issued as a gift card, sometimes a gift card was itself used as a refund, and sometimes it was just a standalone gift card. The REST API didn't distinguish these cases reliably, causing the pipeline to either double-count or miss amounts depending on transaction type.
- Fixed by mapping gift card transactions through GraphQL and applying explicit classification logic before loading into the sales fact table.

### **Proposal Notes — Daily Sync / Migration Strategy (ADF)**

We completed a PostgreSQL to MSSQL migration using Azure Data Factory (ADF) copy activities with daily synchronization, giving us direct hands-on experience with this pattern.

**Key questions that determine the right daily sync approach:**

- **Timestamp Strategy**: Do source tables have `updated_at` or `modified_date` columns? Critical for incremental syncs to identify new and changed records without full-table scans.
- **Deletion Handling**: Are deletes hard (physical remove) or soft (flags like `is_deleted` / `is_archived`)? This determines how change tracking is implemented.
- **Schema Flexibility**: Can timestamp columns be added to existing tables, or must we work with the current schema? If not, database-level triggers can track changes without touching the application.

**Solution recommendations by complexity:**

- **ADF only** — best for straightforward data movement; handles scheduling, copy, and incremental loads with minimal custom code. Used this successfully for RDS → MSSQL migration.
- **Custom Node.js script** — better when complex business logic, custom validation, or edge-case transformations are needed that ADF pipelines can't express cleanly.
- **Hybrid** — ADF for bulk/incremental loads, Node.js for transformation logic that sits outside ADF's native capability.

**Additional scoping questions before design:**
- What is the data volume per full sync? (Determines whether weekly full syncs are feasible vs. daily incremental only)
- Where is the target MSSQL server hosted? (Affects IR selection and network topology in ADF)
- Is a read replica available for sync operations to avoid production performance impact?
