Hey there,
To move fast with the right trade‑offs, I recommend one of two clear paths and can implement either:
- Option A — Next.js App Router only: Route Handlers as your API for a single, streamlined codebase (ideal DX, simple deploys).
- Option B — NestJS backend + Next.js frontend: dedicated API service when you need richer middleware, queues, or websockets.

I’m a backend‑focused full‑stack engineer (5+ years) with production experience in both approaches (Next.js App Router and NestJS) and hands‑on MongoDB (native driver/Mongoose).

- When to choose A: simple→medium APIs, Vercel‑first deployment, rapid delivery, minimal background processing.
- When to choose B: complex domains/integrations, heavy background jobs, socket traffic, or you want the NestJS ecosystem.

What App Router cannot do (or does poorly) — from experience:
- Express middleware/custom server: Not supported in Next.js 13+ App Router. You cannot mount an Express app inside Next on Vercel. If you need Express/NestJS middleware ecosystem, use a separate backend (Option B).
- Long‑lived connections (WebSockets): Vercel serverless functions are short‑lived; persistent WS connections are unreliable. Use a dedicated WS service (Pusher/Ably/Supabase Realtime) or run a separate Node/NestJS service with a long‑running process (Option B).
- Heavy/background jobs: Serverless runtimes time out. Offload to queues/workers (SQS/BullMQ) or a separate service. Scheduled work should use an external scheduler (Vercel Cron is fine for light jobs).
- Stripe webhooks: Possible with App Router, but use Node.js runtime (not Edge) and verify signatures with the raw body buffer. Keep handlers fast and idempotent; for very high volume, consider a small dedicated Node/NestJS webhook service to avoid cold‑start variance.
